# Voxy 26.2 Vulkan 迁移研究与设计

状态：无 shaderpack 的正式 Vulkan normal 链已通过真实世界冷启动/正常退出和首次用户正式视觉测试；
validation layer、resize/reload、Iris、压力、多 vendor 与最终 OpenGL 退役仍未完成
更新时间：2026-07-15  
目标分支：`26.2-vulkan`

## 1. 目标与边界

本分支的目标是在以下版本保持不变的前提下，将 Voxy 的正式渲染路径从 OpenGL 迁移到 Minecraft 26.2 的 Vulkan 后端：

| 组件 | 固定版本 |
| --- | --- |
| Minecraft | 26.2 |
| Fabric Loader | 0.19.3 |
| Fabric API | 0.152.2+26.2 |
| Sodium | mc26.2-0.9.1-fabric |
| Iris（运行时） | 1.11.2+26.2-fabric |
| Java | 25 |

迁移必须保留原 Voxy 的数据布局、所有权、GPU 生成命令、分层遮挡遍历和 MDIC 性能语义。以下方案不属于正式路线：

- 由 CPU 代替 Voxy 的 GPU cmdgen；
- 用固定最大 draw count 代替 indirect-count；
- 创建与 Minecraft 无关的第二套 `VkInstance` / `VkDevice`；
- 保留 OpenGL renderer 作为 Vulkan 路径内部的回退；
- 用预览渲染器、合成数据或离屏样例宣称正式路径可用。

如果 Minecraft 因设备能力不足而回退到 OpenGL，本分支中的 Voxy Vulkan renderer 应给出明确的不兼容信息并停止初始化，而不是静默切换为另一条渲染路线。

## 3. 上游 Vulkan 架构结论

### 3.1 Minecraft 26.2

Minecraft 26.2 已包含 OpenGL/Vulkan 双后端，但 Vulkan 仍是实验选项。当前 `Default` 等价于优先 OpenGL；测试本分支时必须选择 `Prefer Vulkan (Experimental)`。

Blaze3D 的公共层次为：

```text
GpuDevice
 -> GpuDeviceBackend
CommandEncoder
 -> CommandEncoderBackend
RenderPass
 -> RenderPassBackend
RenderPipeline
 -> CompiledRenderPipeline
```

Vulkan 后端持有 Minecraft 的 `VkInstance`、logical device、VMA allocator、graphics/compute/transfer queues、command pools、timeline semaphore 和延迟销毁队列。它使用 dynamic rendering，并把提交控制在 Minecraft 自己的 frames-in-flight 生命周期中。

Minecraft 当前 Vulkan 后端要求 Vulkan 1.2，以及 dynamic rendering、push descriptor、synchronization2、vertex attribute divisor、swapchain 等扩展/功能。公开 Blaze3D API 可以表达：

- vertex/index/uniform buffer；
- sampled texture、render attachment；
- vertex/fragment graphics pipeline；
- direct draw 和固定数量的 indirect draw；
- buffer/texture copy、readback 和 fence。

但它不能表达 Voxy 正式路径所需的：

- storage buffer / SSBO；
- storage image；
- compute shader/pipeline/dispatch；
- indirect dispatch；
- `vkCmdDrawIndexedIndirectCount`；
- Voxy 所需的精确 compute-to-draw barriers。

因此，纯粹使用 Blaze3D 公共 API 无法迁移 Voxy 的 HOC、NodeCleaner、GPU cmdgen 和 MDIC 链。

### 3.2 Sodium 0.9.1

Sodium 0.9 将绝大部分绘制迁移到了 Blaze3D：用 `GpuDevice` 管理资源，用 `RenderPass` 设置附件、pipeline 和 draw。它只在 Blaze3D 不足的少量位置通过 mixin 解包 Vulkan 对象，例如：

- 判断当前 `GpuDeviceBackend` 是否为 `VulkanDevice`；
- 取得 `VulkanRenderPass` 内部的 command buffer；
- 给 Sodium pipeline 增加 push constant range；
- 在 raw Vulkan command buffer 上写 region translation/id push constants。

Sodium 的 Vulkan indirect renderer 由 CPU 生成 `VkDrawIndexedIndirectCommand`，写入 mapped ring buffer，再调用 Blaze3D 的固定数量 indirect draw。0.9.1 的一个修复就是根据 section 数量动态扩展这个 ring buffer。

这条路线适合 Sodium，但不能成为 Voxy 的正式路线：Voxy 的 draw commands、draw count 和 visibility 原本由 GPU compute 生成，替换为 CPU 生成会改变其所有权、吞吐和扩展性。

### 3.3 Fabric Loader 与 Fabric API

Fabric Loader 不参与图形设备创建或渲染命令，可以保持 0.19.3 不变。

Fabric API 0.152.2 提供的是较高层的渲染扩展和生命周期入口，没有 compute、storage buffer、descriptor 或 indirect-count API。较新的 0.154.2 增加了一些高层 render/submit 扩展，但仍未提供 Voxy 需要的底层 Vulkan 能力，因此本迁移没有升级 Fabric API 的必要。

## 4. OpenGL 与 Vulkan 的实质差异

| 当前 OpenGL 模型 | Vulkan 模型 | 对 Voxy 的影响 |
| --- | --- | --- |
| 全局 context 和隐式状态 | 显式 command buffer 和 pipeline | 删除保存/恢复 GL 状态的代码；每个 pass 显式声明状态 |
| driver 管理内存和大部分 hazard | 显式 usage、memory、stage/access dependency | 为 upload、compute、indirect draw、采样和 readback 建立 barrier 表 |
| 运行时 GLSL program | SPIR-V shader module | 用 shaderc 编译，并用反射校验 descriptor/push constant 布局 |
| SSBO、sampler 等拥有独立 binding namespace | 同一 descriptor set 中 binding 必须唯一 | 重新制定 Vulkan binding schema；不能机械保留所有 GL binding 数字 |
| `glMemoryBarrier` | `vkCmdPipelineBarrier2` | 把笼统 barrier 转为精确的生产者/消费者依赖 |
| `glMultiDrawElementsIndirectCountARB` | `vkCmdDrawIndexedIndirectCount` | logical device 创建前必须启用 `drawIndirectCount` feature |
| GL fence 后释放对象 | 多帧并行下延迟销毁 | 资源销毁必须接入 Minecraft 的 submission 生命周期 |

Vulkan 规范明确要求启用 `drawIndirectCount` 后才能调用 indirect-count draw：

- [VkPhysicalDeviceVulkan12Features](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceVulkan12Features.html)
- [vkCmdDrawIndexedIndirectCount](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdDrawIndexedIndirectCount.html)

Minecraft 26.2 当前创建 logical device 时没有启用该 feature。这是第一项硬阻断点，必须在 device 创建前通过最小范围的 mixin 将其加入 required feature 集合；不支持该 feature 的物理设备不能运行正式 Voxy Vulkan 路线。

## 5. 当前 Voxy 路径的保留与重写边界

### 5.1 原样保留的 CPU 数据链

```text
WorldEngine / WorldSection / Mapper
 -> ModelBakerySubsystem / ModelFactory 的 CPU 烘焙部分
 -> RenderGenerationService / RenderDataFactory / BuiltSection
 -> RenderDistanceTracker
 -> AsyncNodeManager 的 CPU 队列、ID 和所有权
 -> Viewport 的相机、frustum 和坐标计算
```

以下二进制契约也必须保持：model records、section metadata、8-byte geometry element、node/visibility/indirect command 布局，以及原有 atlas/mip 语义。

### 5.2 必须改写的 GPU 所有者

- `client/core/gl/*`；
- `UploadStream`、`DownloadStream`；
- `BasicSectionGeometryData` 的资源分配；
- `AsyncNodeManager.tick` 的 GPU memcpy/scatter；
- `NodeCleaner`；
- `HierarchicalOcclusionTraverser`；
- `MDICViewport`、`MDICSectionRenderer`；
- `HiZBuffer`、depth/stencil attachment 和 framebuffer 所有者；
- `ModelStore` 的 GPU buffer、atlas、sampler；
- `SoftwareModelTextureBakery` 的 atlas readback；
- `ModelFactory` 的纹理上传；
- terrain、SSAO、fullscreen/composite pipeline；
- `RenderProperties` 中返回 GL enum 的 depth compare 接口。

当前最早的后端硬编码出现在 Sodium mixin：它把 Minecraft 的 target views 强制转换成 `GlTextureView` 并传递 GL ID。迁移后接口应传递 backend-neutral `GpuTextureView`，在 Vulkan bridge 内部取得 Vulkan image view。

必须保留的正式 GPU 顺序是：

```text
geometry upload/scatter
 -> NodeCleaner
 -> hierarchical occlusion traversal
 -> MDIC prep
 -> cull raster
 -> cmdgen compute
 -> prefix sum
 -> translucent command generation
 -> opaque / temporal / translucent indirect-count draws
```

## 6. 推荐架构：Blaze3D 托管的 Voxy Vulkan 扩展

```text
Minecraft VulkanDevice
  owns VkDevice / VMA / queues / target images / submission lifetime
        |
        v
VoxyVulkanContext
  backend access + capabilities + resource lifetime + synchronization
        |
        +--> Voxy Vulkan compute pipelines
        +--> Voxy Vulkan terrain graphics pipelines
        +--> descriptor/push-descriptor bindings
        +--> raw indirect-count draw
        |
        v
original Voxy geometry -> HOC -> cmdgen -> MDIC render chain
```

设计决策：

1. 不创建第二个 Vulkan device，所有 Voxy GPU 对象都使用 Minecraft 的 device 和 VMA。
2. 初始实现只使用 Minecraft graphics queue。compute 与 draw 按原顺序进入同一 queue；专用 compute queue 只作为完成 parity 后的可选优化。
3. attachment、render target 和 dynamic rendering 生命周期尽量交给 Blaze3D；Voxy 在 active Vulkan render pass 中绑定自己的 raw graphics pipeline 和 descriptors。
4. Voxy compute 使用 Minecraft command encoder 提供的 transient command buffer/execute 接口插入同一 submission。
5. storage resources 使用 Minecraft 的 device/VMA 和延迟销毁机制。可安全复用 `GpuBuffer` 时复用；公共 usage 无法表达 storage 时，使用 Voxy-owned Vulkan wrapper，但不能拥有独立 device/lifetime。
6. 使用 Minecraft 已要求的 `VK_KHR_push_descriptor` 简化 descriptor 更新；每个 pipeline 使用唯一、可反射校验的 binding schema。
7. shader 统一通过 shaderc 编译为 SPIR-V，使用 SPIRV-Cross/反射校验资源契约。
8. quad 数据显式使用现有的 32-bit `ivec2` 路线，不要求 `shaderInt64`；正式 shader 的
   SPIR-V reflection 也拒绝 `Int64` capability，防止它重新成为隐式设备要求。
9. GL barrier 全部改为 synchronization2 的显式 stage/access dependency。
10. 保持 Minecraft 当前 texture `GENERAL` layout 约定，除非实测证明需要更细的 layout transition。
11. 原 MDIC cull 的 representative-fragment capability 分支映射为可选
    `VK_NV_representative_fragment_test` extension/feature：仅在物理设备同时支持时于 Minecraft
    logical-device 创建前启用，并只链入 cull pipeline；不支持时与原 OpenGL 分支一样关闭，
    不作为 fallback，也不改变 cull shader 或 visibility 写入算法。

## 7. 分轮实施计划

| 轮次 | 内容 | 完成门槛 | 估算 |
| --- | --- | --- | --- |
| I — Vulkan Host Contract | 后端识别、Vulkan-only gate、启用 `drawIndirectCount`、读取 limits/features、最小 accessor | `Prefer Vulkan` 下能建立上下文；OpenGL/fallback 时明确拒绝；无 Voxy GL 初始化 | 3–5 天 |
| II — Resource & Synchronization | buffer/texture/sampler、VMA、staging、readback、延迟销毁、barrier 表 | 多帧 copy/readback 正确；validation layer 无生命周期/同步错误 | 1–2 周 |
| III — Shader & Pipeline | GLSL 预处理、shaderc、SPIR-V 反射、descriptor schema、compute/graphics pipeline cache | 所有正式 shader 可编译；binding/push constant 自动校验 | 1–2 周 |
| IV — Model & Geometry | `ModelStore`、atlas、模型上传、geometry arena、metadata、GPU memcpy/scatter | GPU readback 与既有 model/metadata/geometry 二进制契约一致 | 1–2 周 |
| V — HOC & Cleaner | cleaner、HiZ、HOC ping-pong queue、indirect dispatch、request readback | 正式 traversal 全部在 GPU；queue/request/visibility 契约保持 | 2–3 周 |
| VI — MDIC | prep、cull、cmdgen、prefix、translucent generation、indirect-count draw | draw command/count 由 GPU 生成；实际调用 `vkCmdDrawIndexedIndirectCount` | 2–3 周 |
| VII — Render Integration | Sodium target views、reversed-Z、depth/stencil mask、opaque、temporal、SSAO、translucent、composite | 可进入世界；无 validation error；LOD、水体、接缝、洞和昼夜表现通过实景检查 | 2–4 周 |
| VIII — Formal Ownership & Lifecycle | 接通正式 renderer factory、world/session/reload/resize/shutdown 生命周期、Fabric/mixin 边界 | Vulkan 正式 owner 完整接管；旧 GL renderer 不初始化或执行 | 1–2 周 |
| IX — Iris & Shaderpack | 读取 Iris 1.11.2 Vulkan 源码，迁移 shader patch、shadow、deferred/composite 合同 | shaderpack 开关与重载稳定；真实 shaderpack 通过视觉与 validation 检查 | 3–6 周 |
| X — OpenGL Retirement | 按等价 owner 证据删除 GL resources/shaders/mixins，审计单 device、单 resource graph、单 draw route | 正式 client renderer 无 OpenGL owner、fallback、preview 或替代链 | 3–5 天 |
| XI — Validation & Performance | 实景矩阵、压力/泄漏、同场景性能、驱动兼容、dedicated-server 边界 | validation 无未解释错误；长时稳定；性能和支持矩阵有证据 | 1–2 周，另受硬件可用性约束 |
| XII — Final Readiness | 最终 gate、文档、版本、诊断清理、diff/status 与合法性审计 | 完整 TODO 全部有证据并勾选，才能宣布彻底完成 | 2–4 天 |

Iris/shaderpack 兼容是正常 Vulkan renderer 闭环后的独立 Round IX。旧的 OpenGL shader patch 合约不能直接假定可复用；预计额外需要 3–6 周调查和适配。详细任务和实时完成状态只以 `docs/26.2-vulkan-migration-todo.md` 为准。

## 8. 项目难度

总体难度：**9/10，渲染后端级重构**。

这不是 API 名称替换，而是同时迁移以下系统：

- GPU 资源所有权和多帧生命周期；
- compute/graphics pipeline 与 SPIR-V shader 合约；
- descriptor layout；
- GPU-to-GPU、compute-to-indirect、depth-to-sampling 同步；
- Voxy 的 HOC/cmdgen/MDIC 正式链；
- Minecraft/Sodium 的 render target 和 reversed-Z 集成；
- 大型 geometry arena 的显存预算与重用；
- 资源重载、世界切换和退出时的安全销毁。

按一名熟悉 Vulkan、Blaze3D 和 Voxy 数据链的工程师全职计算：

- 正常 Vulkan renderer 达到功能 parity：约 **10–18 工程周**；
- 加上稳定性、性能调优与广泛 GPU 兼容：约 **12–22 工程周**；
- 再加入 Iris/shaderpack parity：额外约 **3–6 工程周**。

这是工程量区间，不是发布日期承诺。最大的不确定性来自 Minecraft 私有 Vulkan 后端的变动、shader descriptor 重构、不同 GPU 驱动的同步差异，以及 Iris 对 Vulkan pipeline 的实际接入方式。

## 9. 主要风险与控制方式

| 风险 | 等级 | 控制方式 |
| --- | --- | --- |
| Minecraft logical device 未启用 `drawIndirectCount` | 极高 | Round I 最先验证并设为 required feature；失败时停止正式 renderer |
| Blaze3D 没有 compute/storage API | 极高 | 建立最小 Vulkan bridge；共享 Minecraft device/VMA/submission，不另起后端 |
| GL/Vulkan binding namespace 不兼容 | 高 | 制定唯一 binding schema；SPIR-V 反射自动验证 |
| barrier 或资源销毁错误只在特定 GPU 出现 | 极高 | 全程开启 validation；建立资源状态表；长时多帧压力测试 |
| geometry arena 过大导致 committed allocation 失败 | 高 | 查询 VMA budget 和 `maxStorageBufferRange`；保留配置上限与复用，按预算确定单一正式容量 |
| Vulkan shader 与原 GL shader 行为偏差 | 高 | 保留二进制布局和算法；逐阶段 GPU readback/可视化探针只作诊断，不作为 readiness |
| Iris/shaderpack 合约未知 | 高 | 正常 Vulkan renderer 先独立闭环，再单独追踪 Iris 1.11.2 Vulkan 路径 |

## 10. 首个实施范围

建议下一步只实施 Round I，不立即迁移 terrain draw：

1. 新建 `VoxyVulkanContext` 及最小 Minecraft Vulkan backend accessors；
2. 在 device 创建前要求 `drawIndirectCount`；
3. 读取并记录 physical device、queue、subgroup、descriptor、storage-buffer 和 indirect limits；
4. 检测 Minecraft 是否实际选择 Vulkan，而不是仅配置了 `Prefer Vulkan` 后又回退；
5. 保证该路径没有创建第二个 Vulkan device，也没有初始化任何 Voxy GL owner；
6. 编译后运行客户端，用 Vulkan validation 验证初始化和退出生命周期。

只有 Round I 证明宿主 device 合同成立后，才进入资源层和 shader pipeline。这样可以在最小改动阶段暴露最致命的平台阻断点。

### 10.1 Round I 实施结果（2026-07-15）

Round I 已建立以下正式宿主合同：

- 通过 Voxy 自有 `GpuDevice` accessor 取得 Minecraft 实际 `GpuDeviceBackend`；
- 只接受 `VulkanDevice`，实际为 OpenGL 或 Minecraft 回退 OpenGL 时明确禁用 Voxy，不运行 fallback；
- 在 `VulkanBackend` class initialization 结束时把 `drawIndirectCount`、
  `drawIndirectFirstInstance` 和 `fragmentStoresAndAtomics` 加入 Minecraft required feature
  集合，使物理设备筛选和 logical-device feature enable 使用同一要求；
  `drawIndirectFirstInstance` 用于保持 MDIC command 非零 `baseInstance` 对应 Vulkan
  `firstInstance` 的硬合同，`fragmentStoresAndAtomics` 用于保持原 cull fragment shader 对
  visibility buffer 的 GPU 写入；cull vertex shader 只读取该 buffer，显式反射为 `NonWritable`；
- 直接复用 Minecraft 的 `VkDevice`、VMA allocator 和 graphics/compute/transfer queues，没有创建第二套 Vulkan device；
- 查询并保存 storage buffer、push descriptor、indirect draw、compute 和 subgroup limits；
- 在 Minecraft 销毁 Vulkan device 前清除 Voxy host context；
- 正式 Vulkan renderer 尚未贯通时保持 readiness gate 为 false，明确阻止旧 `VoxyRenderSystem` OpenGL owner 创建。

本机运行证据：

```text

device=NVIDIA GeForce RTX 5070 Ti
graphicsQueueFamily=0
computeQueueFamily=2
transferQueueFamily=1
maxStorageBufferRange=4294967295
maxPushConstantsSize=256
maxPushDescriptors=32
maxDrawIndirectCount=4294967295
maxPerStageDescriptorStorageBuffers=1048576

```

Round I 当时的验证结果：`compileJava` 通过；`runClient` 确认 Minecraft 实际使用 Vulkan，
host context 正常建立并在客户端正常关闭时先于宿主 device 释放。日志中没有创建 Voxy OpenGL
renderer。该阶段资源层、shader pipeline、HOC、cmdgen 和 MDIC 尚未迁移；后续现状见 10.2–10.4。

### 10.2 Round II 当前进展（2026-07-15）

已建立第一组 Vulkan 资源 owner：

- `VoxyVulkanBuffer`：原未映射 `GlBuffer` 的 device-local Vulkan 等价 owner；buffer 由 Minecraft 的 `VkDevice`/VMA 创建，并通过 Minecraft command encoder 的 deferred-destruction queue 回收；
- `VulkanUploadStream`：保留原 64 MiB staging、至少 16 字节/SSBO alignment、裸地址写入和批量 copy 合同；实际 staging storage 由 Minecraft transient memory 提供，copy 进入当前 graphics-queue submission；
- `VulkanDownloadStream`：使用 Minecraft VMA 创建一个全局 32 MiB 持久映射 readback ring，
  保留原 `DownloadStream.INSTANCE` 的 `AllocationArena` 区段 ownership、copy 后按 submit fence
  排队、顺序轮询、异步 callback 和“callback 返回后指针失效”的合同。锁定的 Minecraft 26.2
  `VulkanGpuBuffer.Direct` 对 MAP_READ 强制 `HOST_VISIBLE | HOST_COHERENT` 并优选
  HOST_CACHED；因此 fence 完成和 `TRANSFER_WRITE -> HOST_READ` dependency 后无需额外 VMA
  invalidate。不得把 transient staging 的 mapped pointer 保留到未来帧 callback；其 allocator
  可以在 submission 轮转后复用同一区段；
- upload 返回的 `ByteBuffer` 显式固定为 native byte order，以保持原裸指针写入的二进制语义。

开发期间使用临时 GPU round-trip probe 验证：CPU 写入 16 字节 staging，复制到带 storage usage 的 device-local Voxy buffer，再经正式 `VulkanDownloadStream` 复制回 host-visible staging；submit fence 完成后的 callback 得到完全一致的四个 32-bit 值。探针验证后已从源码移除，不能作为 renderer readiness 依据。

此后已补齐 central buffer usage policy、GPU fill/zero、精确 synchronization2 buffer/image barrier、VMA image/image-view、host sampler、texture upload、Voxy image readback 与 subresource layout state。Round II 仍未完成的主要部分是 image copy/mipmap 通用路径、全部正式消费者迁移、多 frame/reload 压测和最终单 resource graph 审计。

### 10.3 Round III/IV 当前进展（2026-07-15）

已建立 Vulkan shader/compute 基础设施：

- 原 `ShaderLoader` include 合同继续作为唯一 shader source loader；外部 defines 先注入，再由 shaderc 预处理条件分支和 symbolic binding，最后转换 Vulkan binding/push constant；
- GL 的 storage-buffer、uniform-buffer、sampler 和 storage-image 独立 namespace 被确定性映射到 Vulkan set 0 的不重叠区间；
- 原 uniform location 按类型 alignment 紧密打包为 push constant；location 不是字节 offset，shaderc 后由 SPIRV-Cross 同时校验 push block 总大小与每个 member offset；
- shaderc 输出 SPIR-V，SPIRV-Cross 反射 descriptor、set/binding、buffer member offset 和 push-constant size；编译器启用与 Minecraft 26.2 一致的 `auto_map_locations`，并保留原 `IS_INTEL`、`IS_WINDOWS`、printf-disabled 和 zero-to-one depth 合同；
- descriptor-set layout 使用 `VK_KHR_push_descriptor`，pipeline layout 数量受实际 `maxPushDescriptors` 限制；device-scoped pipeline cache、compute pipeline 与 dynamic-rendering graphics pipeline 均进入 Voxy Vulkan context 的延迟销毁顺序；
- graphics pipeline 的 depth/stencil state 不再只有 depth 三元组：front/back stencil 的 compare、fail/pass/depth-fail、compare/write mask 与 reference 都是强制显式合同；启用 stencil 时缺少 attachment format 会 fail-fast，禁用也必须显式选择，避免后续 depth/stencil mask pass 静默继承错误默认值；
- raw compute pipeline 和 dispatch 进入 Minecraft 当前 graphics submission，不创建第二 queue/device；
- debug `GPUTiming` 保留原 marker、帧后非阻塞轮询、区间标签和峰值衰减显示语义，但 query owner 改为 Minecraft 26.2 的 `GpuQueryPool` 与 Vulkan `writeTimestamp`，按宿主 `timestampPeriod` 换算毫秒并在宿主 device shutdown 前延迟销毁；非 Vulkan backend 明确不启用，不再存在可由 debug UI 触发的 OpenGL query 绕行路径；
- 临时 `util/set.comp` probe 已在实际 Vulkan device 上验证 shaderc -> reflection -> pipeline -> push descriptor -> dispatch -> readback，随后删除。
- 全量 shader 合同见 `docs/26.2-vulkan-shader-contracts.md`；全部正式非 Iris base variant 已在实际宿主 Vulkan device 生成 SPIR-V 并通过 descriptor/push reflection，fullscreen vertex/fragment 也已创建实际 dynamic-rendering graphics pipeline。

Round IV 已迁移的正式 owner：

- `SoftwareModelTextureBakery` 不再取得 `GlTexture` 或调用 `glGetTextureImage`，改从 Minecraft `GpuTexture` 走 Vulkan readback；
- `ModelStore` 使用 64-byte-record VMA buffer、colour buffer、RGBA8 四级 atlas、image view 和 host Vulkan sampler；原 GL owner 只生成并上传 16/8/4/2 四级，CPU scratch 因完整幂级数分配多出未写入的 3x2 RGBA（24-byte）尾部，Vulkan 保持该 GPU 合同且不把尾部暴露成第五级；
- `ModelFactory` 保持 CPU 烘焙/判定算法，model/biome/atlas upload 改用 Vulkan staging 与逐 mip image copy；
- `BasicSectionGeometryData` 使用 VMA-backed storage buffer，保持 32-byte metadata 与 8-byte geometry element；原 `BasicAsyncGeometryManager` 的 ID、arena、127-element allocation rounding、free/reuse 和 OOM 合同未改；
- `AllocationArena` 与 `BasicAsyncGeometryManager` 本身相对基线无源码差异，因此 allocation/free、相邻空洞合并、尾部收缩、fragmentation reuse、尾部 expansion、127-element rounding、ID reuse 和 OOM hard-fail 语义保持原样；
- `RenderResourceReuse` 使用 VMA memory budget 和 `maxStorageBufferRange` 确定单一 geometry capacity，并保留原 next-power-of-two/double、Intel 最小 1 GiB、NVIDIA/Linux 最大 2000 MiB、512 MiB 下限和 1.5 GiB 显存余量分支；不再使用 GL sparse-buffer fallback，Vulkan hard limit 不足时明确失败；
- geometry arena 与原 owner 一样在首次分配和 cache reuse 时不整块清零；只有新 metadata 指向的已上传范围可观察。model atlas 仍在每次取出时 GPU 清零；cache 拒绝 closed 或重复归还的对象；
- reuse 后的 buffer overwrite/readback 通过声明资源全部可能 access 到 transfer 的写前/读前 barrier 串联，随后再建立 transfer 到正式 consumer 的依赖；全部命令继续进入 Minecraft 单一 graphics queue，close 进入宿主两帧 destruction queue；
- `AsyncNodeManager` 的 CPU 队列与所有权未改，原 `memcpy.comp`/`scatter.comp` 已建立 Vulkan compute owner；与原 GL dispatch 前后各一次 memory barrier 对应，geometry、node 和 section-metadata 输出在 compute 覆盖写入前先由资源全部声明访问同步到 `COMPUTE_STORAGE_WRITE`，dispatch 后再由 compute write 同步到正式 consumer，避免前帧 traversal/draw 与新写入竞争。

### 10.4 Round V–VIII 正式 normal renderer 当前进展（2026-07-15）

- `VulkanNodeCleaner` 保持三个原 shader、256-entry min/output 合同、visibility frame ID、
  top-bit encoded reset/clear、geometry pressure threshold 和固定 256 `uvec2` 异步 removal
  readback；shutdown 必须在停止 `AsyncNodeManager` 前显式 flush callback。
- `VulkanHiZBuffer` 使用 D24S8、原 4-vertex triangle fan、depth always/write、
  highest-one-bit 尺寸、原 mip 数与精确 `NEAREST_MIPMAP_NEAREST` raw Vulkan sampler；每个
  mip 在 depth attachment write 后转为 sampled。Minecraft depth target 保持 GENERAL layout
  并以显式 transfer-clear/depth-write 到 fragment-sample dependency 暂时切换访问；输入只接受
  单层、单 mip 且尺寸一致的宿主 depth view，使 image barrier 与 descriptor 覆盖同一 subresource。
  Round VII 的 Voxy D24S8 offscreen depth 则通过同一 image owner 从 depth/stencil attachment
  layout 转为 sampled，
  HiZ 完成后恢复 attachment layout，不经 GL texture id 或 CPU copy。
- `VulkanHierarchicalOcclusionTraverser` 保持 request 50、queue 200000、
  `MAX_LOD_LAYER+1` 次迭代、1024-byte scene UBO、16-byte indirect metadata、首轮 direct、
  后续 indirect A/B ping-pong、原 request clamp/callback。queue metadata 的轮间 source
  dependency 同时覆盖 compute read/write 和 indirect-command read，不能只同步 compute；
  traversal 开始前也把上一轮 readback/cleaner/scatter 对 request 与 persistent node buffer
  的访问同步到本轮 compute read/write；最终 render-list、visibility 和 `markRequested`
  修改过的 persistent node buffer 均从 traversal compute write 显式发布到各自正式
  consumer，保持原末尾 storage barrier 合同。
- `VulkanViewport` 与 `VulkanMDICViewport` 已建立原 camera/frustum/section translation、
  D24S8 depth-bounding target 和五组 MDIC buffer 容量/角色 owner；
  `VulkanViewportSelector` 保持 default viewport、Vivecraft render-pass key、Iris shadow key
  和全部额外 viewport 的逐 owner close。
- `VulkanBoundRenderer` 保持原 ready-section/ready-column producer、128-byte uniform、
  32 AABB batching、CW back-face、further-depth compare 与 clear contract；OpenGL byte index
  buffer 等价表示为 Vulkan uint16，索引值、顶点 ID、instance/base-instance 和 draw 分组不变，
  因而不把 `VK_EXT_index_type_uint8` 变成新的硬能力。
- shader 预处理层将 OpenGL `gl_InstanceID` 映射为
  `gl_InstanceIndex - gl_BaseInstance`，因为 Vulkan instance index 包含 firstInstance、
  OpenGL instance ID 不包含 base instance；保留 shader 中显式 `gl_BaseInstance` 后，bounds
  remainder draw 与 MDIC 的原索引语义不被重复偏移。
- `VulkanMDICSectionRenderer` 已建立 prep、cull、cmdgen、prefix、translucent generation、
  opaque/temporal/translucent terrain pipeline 和实际 `vkCmdDrawIndexedIndirectCount` 记录；
  command partition、20-byte stride、12/16/20-byte count offset、GPU count 与原 max-count
  clamp 均保持。Minecraft 26.2 lightmap 的首次 clear 是 transfer write、更新是 color-attachment
  write；terrain sampled-read 前的宿主 barrier 同时覆盖两类正式 producer，并把 image 保持在
  Minecraft 的 GENERAL layout；draw 后的反向 barrier 再把 sampled read 发布给宿主下一次
  transfer/color-attachment write。source depth 同样在 Voxy sampled read 前接收宿主
  transfer/depth-attachment producer，并在 setup 完成后恢复为宿主 depth-attachment consumer
  状态。Voxy image state tracker 对真正相同且无新访问的状态转换仍可省略
  barrier，但连续 dynamic-rendering attachment pass 不能据此省略依赖：depth/stencil setup 的跨帧
  覆盖、setup -> opaque，以及 colour attachment 的 opaque -> temporal/translucent `LOAD` 均使用
  强制 dependency，即使 layout/stage/access 数值未改变也会发出 image barrier。
- terrain vertex shader 通过 `QUAD_DATA_USE_IVEC2` 显式选择原 `quads3.vert` 已有的 32-bit
  分支，继续读取两个 32-bit word 组成的同一条 8-byte quad record；Minecraft logical-device
  required feature 集合不再加入 `shaderInt64`。独立 shaderc/SPIR-V-Cross 探针确认默认扩展分支
  声明 `Int64`，正式 `ivec2` 变体不声明；正式 compiler 还会在 reflection 发现 `Int64` 时 fail-fast。
- `RenderProperties` 的 closer/closer-equal/further depth policy 现以 Minecraft 26.2
  backend-neutral `CompareOp` 为唯一 identity；保留的只读 GL 基线只在原调用点经
  `GlConst.toGl` 适配，正式 Vulkan pipeline 只经 `VulkanConst.toVk` 适配。zero-to-one 与
  reversed-Z shader defines 也来自同一 backend-neutral map，避免两个后端各自重写条件。
- `VoxyRenderSystem`、Sodium/Nvidium 注入点、`VulkanViewportSelector` 与
  `VulkanNormalRenderPipeline.runFrame` 已在源码中把 normal 路线按原顺序收束为：
  bounds/clear -> depth/stencil setup -> opaque -> HiZ -> AsyncNodeManager -> NodeCleaner ->
  HOC -> cmdgen -> temporal -> SSAO -> translucent -> final composite；原 occlusion-debug 0/1
  分支、FREX work loop、world callback、
  异步下载 flush 与逆序销毁责任保持。FREX 原 `glFinish()` 同步点先通过 Minecraft 26.2
  host encoder 提交当前 submission builder，再等待同一 graphics queue；不能仅 queue-idle
  尚未提交的 Voxy command buffers。world/render-system shutdown 也在释放 GPU owner 前执行
  同一 submit-and-wait 合同，即使本轮没有 download frame 触发隐式 submit。Sodium 输入已改为
  宿主 `GpuTextureView`，不再经 `GlTextureView`/GL id；depth、colour 和 lightmap 沿同一次
  `VoxyRenderSystem -> VulkanNormalRenderPipeline` frame call 传递。pipeline 边界明确拒绝非 Vulkan、
  closed、非单 mip/单 layer、aspect 错误或 depth/colour 尺寸不一致的宿主 views，保留原
  `runPipeline(sourceDepth, sourceColour, ...)` ownership，避免 composite 阶段重新猜测 target。
- `VulkanSSAO` 保持原 compute shader、输出 storage image、depth/normal/source-depth 输入和
  dispatch 尺寸；`VulkanMDICSectionRenderer.renderTranslucent` 继续消费 GPU 生成的 translucent
  indirect-count 分区；`VulkanFinalComposite` 使用原 fullscreen quad 合同把 SSAO/translucent
  colour 与 Voxy depth/stencil mask 合成回同一 Minecraft colour target。后半帧不创建 preview、
  offscreen replacement 或第二套 frame scheduler。
- 全局 `VulkanDownloadStream` 只在原 `AbstractRenderPipeline.innerPrimaryWork` 对应的 HOC 主循环
  位置统一 `tick()`。HOC、NodeCleaner 和 MDIC 共享同一 32 MiB ring；owner close 只等待/丢弃
  自身资源仍可能涉及的提交，最终 map/unmap 和 buffer retirement 由 `VoxyVulkanContext` 在
